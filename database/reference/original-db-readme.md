# CareerPilot AI database

One schema in `models.py` generates everything else: the database, SQL files for PostgreSQL and SQLite, an ER diagram, and a data dictionary. It covers students, recruiters and college admins from the product plan, 47 tables in all.

## Quick start

```bash
pip install -r requirements.txt
python generate_db.py all            # creates careerpilot_dev.db with reference + demo data
python generate_db.py generated      # writes ./generated (SQL, ER diagram, data dictionary)
```

| Command | What it does |
|---|---|
| `create [--drop]` | Creates tables and 3 reporting views |
| `seed` | Loads 44 skills, 7 target roles, 30 interview questions, 12 learning links |
| `demo --students 60` | Loads fake students, recruiters, listings, applications, interviews and placements |
| `check` | Row counts, foreign key check and consistency rules |
| `generated` | Rewrites `generated/` from the models |

Use another database with `--url` or `DATABASE_URL`, for example `postgresql+psycopg://user:pass@host/dbname` (add `psycopg[binary]` to your install). Demo data is repeatable with `--seed` and refuses to run when `CAREERPILOT_ENV=production`.

## What is in the schema

| Area | Tables |
|---|---|
| Accounts and safety | users, auth_tokens, user_sessions, consents, data_deletion_requests, audit_log |
| Colleges | colleges, departments, batches, admin_profiles, announcements |
| Students | student_profiles, student_preferences, student_skills, student_projects, project_skills, resumes, resume_extracts |
| Career tools | skills, skill_aliases, job_roles, job_role_skills, learning_resources, skill_gap_analyses, career_paths, career_path_milestones, resume_analyses, interview_questions, practice_answers, readiness_snapshots |
| Recruiters and listings | companies, recruiter_profiles, company_verifications, opportunities, opportunity_skills, opportunity_departments, opportunity_reviews, opportunity_events, opportunity_reports |
| Matching and tracking | recommendations, saved_opportunities, applications, application_status_history, interviews, placements, notifications, notification_preferences |

Views: `v_application_funnel`, `v_applications_by_department`, `v_placements_by_batch`.

## How it maps to the plan's market-readiness list

- **No plain-text passwords:** `users.password_hash` holds a salted hash. The generator uses scrypt from the Python standard library.
- **Email verification, reset, session expiry:** `email_verified_at`, `auth_tokens` (only a SHA-256 of each token is stored), `user_sessions` with expiry and revocation, plus failed-login lockout columns.
- **Resume security:** only a private storage key is stored, never a public URL. The database allows PDF and DOCX only, up to 10 MB, and one current resume per student. Parsed resume text sits in `resume_extracts` so it can be deleted on its own.
- **Consent and deletion:** `consents` records what each user accepted and when. `data_deletion_requests` tracks deletion.
- **No duplicate applications:** a unique constraint on student and listing.
- **Explainable matching:** `recommendations` and `skill_gap_analyses` store the matched, improving and missing skills and a plain-language reason, not just a score.
- **Honest scores:** column comments state that guidance and readiness scores are not ATS scores or placement predictions.
- **Verification and listing history:** `company_verifications`, `opportunity_reviews`, `opportunity_events` and `audit_log` keep the record.
- **Data minimisation:** no IP addresses are stored.

## Things this does not do for you

- **Role-based access is not enforced by the database.** Enforce it in the application on every request. Test that a student cannot read another student's data and that recruiters see only applicants for their own listings. For PostgreSQL, row-level security is a worthwhile extra layer.
- **Backups, restore tests and migrations are still to do.** Use Alembic (`alembic revision --autogenerate`) with these models for migrations on PostgreSQL.
- **The schema is not connected to your current Streamlit app.** Moving from the existing SQLite tables means mapping old columns to the new ones and rewriting the queries.
- **Demo accounts are fake and for development.** Do not load demo data in production. Remove any demo credentials before launch.
- **Learning links are a starter set.** Check each URL before launch.
- **The SQL was parsed as PostgreSQL but not run on a live PostgreSQL server here.** Run `generated/schema.postgres.sql` on a test database first.

## Portability notes

- IDs are UUIDs generated by the application. On SQLite they are stored as text.
- JSON columns become JSONB on PostgreSQL.
- Enums are stored as VARCHAR with CHECK constraints, which keeps migrations simple.
- SQLite needs `PRAGMA foreign_keys=ON`. `generate_db.py` sets it for every connection.
